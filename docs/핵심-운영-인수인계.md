# JW 성경 연구 도우미 핵심 운영 인수인계

- 기준일은 2026-11-05이다. 2026-08-11판에 그 뒤 생긴 React 화면, 카카오 로그인, 자료 보관, 마이페이지, 연설 준비를 반영했다.
- 이 문서는 현재 서비스의 운영과 후속 개발에서 가장 먼저 읽어야 하는 정본이다.
- 결정 과정과 과거 장애의 상세 기록은 `context-notes.md`에 보존되어 있다. 기능별 설계는 `docs/superpowers/specs/`에, 사용법은 `README.md`에 있다.

## 1. 현재 서비스 상태

- 운영 주소는 `https://jw-assistant-seven.vercel.app`이다.
- GitHub 저장소는 `https://github.com/iam-kimleader/jw-assistant`이며 운영 브랜치는 `main`이다.
- Vercel 프로젝트는 `honeskor-1168s-projects/jw-assistant`이고 함수 리전은 서울 `icn1`이다.
- Vercel은 GitHub `main` 브랜치와 연결되어 있어 `main`에 푸시하면 프로덕션 배포가 자동으로 만들어진다. 2026-08-09에 자동 프로덕션 배포가 `READY`와 `PROMOTED` 상태가 되는 것을 확인했다.
- Vercel 런타임은 Node 24.x다. 함수 실행 상한은 Vercel 프로젝트 설정의 300초다.
- 화면은 React, Vite, Tailwind CSS, shadcn/ui로 만들었다(2026-08-26). 빌드 결과는 `web/dist`이고 API는 `api/*.js` Vercel 함수다.
- 홈 화면에서 생활과 봉사, 파수대 연구, 연설이 활성화되어 있다. 개인 연구와 봉사인도는 "준비 중" 카드로만 있고 구현되지 않았다.
- 카카오 계정으로 로그인한다. 초대 코드는 없어서 카카오 계정만 있으면 누구나 들어와 AI 호출을 쓸 수 있다. 회중 규모라 그렇게 정했다.
- 인증 API 셋(`auth-start`, `auth-callback`, `auth-logout`)을 뺀 모든 API가 로그인을 요구한다. 세션이 없으면 401 `로그인이 필요합니다.`를 돌려준다.
- 자료는 비공개 Vercel Blob에 보관한다. 주간 연구 답변은 회중이 함께 쓰는 한 벌이고, 연설 자료와 연사 설정은 사람마다 따로 둔다.
- 마이페이지(`/me`)에서 보관한 연구 답변과 연설을 다시 열고 연사 설정을 고친다. 상단 막대의 닉네임을 누르면 간다.
- 화면에서 선택 가능한 주간은 현재 주를 포함한 이전 10주와 이후 10주로 총 21주다. 서버의 `/api/options`가 정한다.
- 준비 API는 화면의 21주 선택 범위로 제한하지 않는다. 직접 호출 시에는 로그인한 상태에서 `YYYY-MM-DD` 날짜 형식을 검증한 뒤 해당 주간 자료 조회를 시도한다.
- 마지막 전체 테스트 기준은 451개 중 449개 통과, 데이터 원본이 필요한 2개 스킵, 실패 0개다(2026-11-05).

## 2. 절대 지켜야 할 정확성 원칙

1. 성구 인용은 반드시 `core/bible/text/`에서 실제로 읽은 문자열만 사용한다. 기억이나 모델 지식으로 성구 문장을 만들지 않는다.
2. 교리적 설명은 WOL 출판물 근거를 사용한다. 근거가 없으면 `출판물 근거 미확인 — 내 정리임.`이라고 표시한다.
3. 여호와의 증인의 이해를 기준으로 삼고 독자적인 새 교리를 만들지 않는다.
4. 출판물은 공식 WOL URL과 조회 날짜를 함께 보존한다.
5. AI 답변은 연구 보조 초안이다. 공식 출판물이나 성경 본문을 대체하는 권위 있는 답변으로 취급하지 않는다.
6. 출판물 본문은 서버에서 AI 근거로만 사용한다. 브라우저 API 응답과 Blob 보관본에서는 본문을 제거하고 제목, 출판물명, URL, 조회일만 남긴다.
7. `OPENAI_API_KEY`는 서버 환경 변수로만 둔다. 브라우저 코드, 로그, Git에는 절대 넣지 않는다.
8. 이미 보관된 주간을 다시 만드는 동작은 GET에 두지 않는다. 새로 고침이나 미리 가져오기로 호출 비용이 나가면 안 된다. GET은 보관본이 없을 때만 새로 만들고, 다시 만들기는 POST로만 한다.

## 3. 현재 데이터 흐름

### 생활과 봉사와 파수대 연구

1. 브라우저가 선택한 날짜 또는 직접 호출자가 지정한 날짜를 `/api/life-ministry` 또는 `/api/watchtower`에 보낸다.
2. 서버는 먼저 Blob의 그 주 보관본을 찾는다. 있으면 그대로 돌려주고(`보관.새로만듦:false`), 없거나 POST로 다시 만들기를 요청했을 때만 아래 단계로 새로 만든다.
3. 서버가 WOL 주간 페이지에서 해당 교재와 연구 기사를 찾는다.
4. 생활과 봉사는 영적 보물 찾기와 그 주의 회중 성서 연구 서책 및 장을 찾는다.
5. 질문, `(ㄱ)`과 `(ㄴ)` 하위 질문, 소제목, 인용 성구, 삽화를 구조화한다.
6. 성구 본문은 `core/bible/text/`, 상호 참조는 `core/bible/refs/`에서 읽는다.
7. 영적 보물 2는 주간 성경 읽기 장 또는 편 범위 전체를 로컬 성경 코어에서 읽어 전용 AI 근거로 사용한다.
8. 질문에 연결된 WOL 참고 출판물의 정확한 항 범위를 `src/wol-reference-map.json`으로 찾고 실제 `/d/` 문서를 읽는다.
9. OpenAI Responses API가 출판물 문장, 참고 출판물 본문, 성구 본문, 삽화를 근거로 답변을 만든다.
10. 서버가 출판물 본문과 주간 읽기 전체 본문을 제거한 뒤 답변, 선택 성구, 클릭 가능한 공식 링크만 브라우저에 반환하고, 같은 것을 Blob에 회중 공용본으로 저장한다.
11. 화면은 답변만 복사하며 참고 성구와 출판물 정보는 클립보드에 넣지 않는다.

### 연설 준비

1. `/api/talk-assignments`가 그 주 생활과 봉사 교재를 WOL에서 읽어 연사 설정에 맞는 연설 배정과 공개강연 카드를 돌려준다. 저장하지 않는다.
2. `/api/talk-outline`이 뼈대를 만든다. 보물 연설과 공개강연은 규칙으로, 나머지 배정은 AI로 만든다. 배정이 가리키는 출판물을 서버가 읽어(배정당 4편, 모델에 넘기는 본문 합계 16,000자) 근거로 쓰고, 뼈대에는 본문을 뺀 참조만 담아 저장한다.
3. `/api/talk-draft`가 원고를 만든다. 서버가 출판물을 한 번 더 읽어 모델에 넘기고, 성구는 로컬 성경 코어에서 채우고, 원고 속 인용이 근거 원문에 글자 그대로 없으면 경고로 남긴다. 뼈대와 원고를 함께 저장한다.
4. `/api/my-talk`는 저장한 연설을 돌려주거나 지운다. `/api/my-archive`는 마이페이지 목록(회중 공용 연구 답변 전체와 내 연설)을 돌려주고, `/api/my-profile`은 연사 설정을 저장한다.

### 로그인과 보관

1. `/api/auth-start`가 `jw_state` 쿠키(10분)를 두고 카카오 인증 화면으로 보낸다.
2. `/api/auth-callback`이 state를 확인하고 카카오 사용자 정보를 읽는다. 회원번호는 카카오 id다. 처음 로그인하면 `users/{회원번호}/profile.json`을 만든다. 그 뒤 HMAC으로 서명한 `jw_session` 쿠키(30일)를 두고 `/`로 보낸다. 실패하면 `/login?오류=…`로 보낸다.
3. `/api/auth-logout`은 POST로만 받고 세션 쿠키를 지운다.
4. Blob 경로는 `src/storage-paths.mjs`가 만든다. 브라우저는 경로 조각을 보내지 않고 날짜와 배정 번호만 보낸다.
   - `weeks/{watchtower|life-ministry}/{그 주 월요일}.json` 은 회중 공용 연구 답변이다.
   - `users/{회원번호}/profile.json` 은 닉네임, 첫 로그인 때, 연사 설정이다.
   - `users/{회원번호}/talks/{주간}-{배정번호}.json` 은 연설 뼈대와 원고다.

## 4. 다시 겪으면 안 되는 핵심 장애와 해결법

### Vercel 함수에 성경 코어가 빠지는 문제

Vercel은 `fs`로 읽는 `core/bible/**` 파일을 자동으로 함수 번들에 넣지 못했다. 이 설정을 제거하면 운영 API가 `core/bible/index.json`을 찾지 못한다.

```json
"functions": {
  "api/*.js": {
    "includeFiles": "core/bible/**"
  }
}
```

### 새 화면 주소는 `vercel.json`에도 넣는다

`vercel.json`은 화면 주소를 `rewrites`에 하나씩 열거한다. 로컬 서버 `src/web-server.mjs`는 확장자 없는 경로면 무조건 `index.html`을 주므로, 타입 검사와 빌드와 SSR 스모크가 모두 통과한 채로 배포에서만 404가 난다. 그 화면에서 새로 고침하거나 링크를 공유할 때 드러난다. `/me`, `/login`, `/invite` 때 실제로 겪었다. `web/src/App.tsx`에 라우트를 더하면 같은 커밋에서 `vercel.json`에도 넣는다. `api/*.js`와 `src/web-server.mjs`의 API 목록도 서로 같아야 한다.

### `vercel.json`에 `maxDuration`을 두지 않는다

`vercel.json`의 `maxDuration` 60이 프로젝트 설정 300초를 덮어써 긴 생성이 잘린 적이 있다(2026-08-25). 함수 상한은 프로젝트 설정에서만 정한다.

### Vercel에서 WOL 요청이 불안정한 문제

`src/wol-fetch.mjs`의 IPv4 우선 DNS, `Accept-Encoding: identity`, Node `https` 폴백, 제한 시간과 오류 요약은 운영 안정성을 위해 필요하다. 일반적인 `fetch` 한 줄로 되돌리지 않는다.

WOL의 `/pc/` 참고 링크는 로컬에서는 307 리디렉션을 주지만 Vercel에서는 서울 리전에서도 반복해서 `ETIMEDOUT`이 났다. 반면 실제 기사 `/d/` 경로는 정상 동작했다. 그래서 `/pc/` 링크를 운영 중에 직접 해석하지 않고 로컬에서 정확한 `/d/...#h=` 범위로 미리 해석해 `src/wol-reference-map.json`에 저장한다.

### 참조 매니페스트는 매주 자동으로 갱신한다

`src/wol-reference-map.json`은 선택 가능한 21주의 WOL `/pc/` 참고 링크를 정확한 `/d/...#h=` 범위로 미리 풀어 둔 목록이다. 연구 답변과 연설 준비가 모두 이것을 읽는다. 날짜 범위가 매주 이동하므로 매주 다시 만들어야 한다.

GitHub Actions 워크플로 `.github/workflows/refresh-references.yml`이 매주 월요일 05:00(한국 시간)에 GitHub 서버에서 `npm run refresh:references`와 `npm test`를 돌리고, 목록이 바뀌었으면 커밋해 `main`에 푸시한다. 그 푸시로 Vercel 배포가 따라온다. 풀지 못한 링크가 있으면 푼 만큼은 저장하고 실행을 실패로 끝내므로, GitHub이 저장소 주인에게 실패를 메일로 알린다. 바로 돌려야 할 때는 저장소의 Actions 탭에서 이 워크플로를 고르고 `Run workflow`를 누른다. 공개 저장소는 60일 동안 활동이 없으면 GitHub이 예약 실행을 멈춘다. 그때는 Actions 탭에서 이 워크플로를 다시 켠다.

2026-08-08에 처음 만든 뒤 2026-11-05까지 갱신하지 않아, 10월 19일 주부터는 참고 링크가 하나도 목록에 없었다. 그래서 자동 갱신을 만들었다.

매니페스트에 없는 링크는 짧은 실시간 해석을 시도하지만 Vercel에서는 실패할 가능성이 높다. 이를 정상적인 주 경로로 의존하지 않는다.

### 교본 매니페스트는 교본이 바뀔 때만 다시 만든다

`src/teaching-lessons.json`은 「읽가」 20과와 「랑제」 12과의 과별 요점을 담는다. 런타임은 이 파일만 읽으므로 연설 준비는 그 과의 링크를 따로 읽지 않는다. 두 교본이 개정되었거나 교재가 인용하는 과가 매니페스트에 없을 때 `npm run refresh:teaching-lessons`로 다시 만든다. 추출한 과 수가 기준선보다 적으면 파일을 쓰지 않고 실패로 끝난다.

### 회중 성서 연구 서책은 완전 자동이 아니다

생활과 봉사 교재에서 서책명과 장을 읽지만 WOL 출판물 심벌은 `src/ministry-meeting.mjs`의 `서책심벌`에 등록되어 있어야 한다. 현재 확인된 값은 `용하 → wcg`, `순 → rr`이다. 회중 성서 연구 서책이 바뀌면 새 약칭과 WOL 심벌을 확인해 이 표에 추가하고 실제 주간 API로 검증해야 한다.

`용하`는 질문에 기존 `class="qu"` 대신 질문 바로 뒤의 `div.gen-field`를 사용한다. `src/wol-article.mjs`의 대화형 서책 폴백을 제거하면 회중 성서 연구 질문이 사라진다.

### OpenAI에 WOL 이미지 URL을 직접 보내면 실패한다

OpenAI가 WOL 원격 이미지 URL을 `400 invalid_value`로 거부했다. `src/ai-answer.mjs`는 서버에서 이미지를 먼저 내려받아 Base64 데이터 URL로 변환한 뒤 입력한다. 이 경로가 삽화 추론의 필수 조건이다.

### 영적 보물 2는 다른 질문의 자료를 사용하면 안 된다

`이번 주 성경 읽기를 통해 어떤 영적 보물을 발견했습니까?`에는 질문 자체의 인용 성구가 없다. 이 질문에 근거를 따로 주지 않으면 같은 AI 요청의 회중 성서 연구 내용이 섞일 수 있다. `src/weekly-reading.mjs`가 교재 날짜 아래의 `성경범위`를 로컬 성경 코어에서 모두 펼쳐 이 질문에만 제공한다.

AI는 제공된 범위 안의 특정 성구 주소를 `selectedVerse`로 반환해야 한다. 서버가 주소를 검증하며 범위 밖 성구이거나 빈 값이면 AI 답변을 채택하지 않는다. API에는 전체 읽기 본문을 내보내지 않고 최종 선택 성구 하나만 표시한다.

### AI 요청은 길고 부분 실패가 가능하다

15개 답변을 한 요청으로 만들면 180초를 넘겼다. 연구 답변의 기본 모델은 `gpt-5.6-terra`, 추론 강도는 `high`, 묶음 크기는 5개이며 여러 묶음을 병렬 실행한다. 각 OpenAI 요청 제한 시간은 120초다.

묶음 일부만 실패하면 성공한 AI 답변은 유지하고 실패한 묶음만 공식 자료 기반 초안으로 돌린다. API 키가 없거나 전체 호출이 실패해도 서비스는 폴백 답변을 반환해야 한다.

실제 2026년 8월 3일 주간 생활과 봉사 운영 검증은 약 125.3초가 걸렸고 15개 답변 모두 AI 모드로 생성됐다. 성능 변경 뒤에는 짧은 단위 테스트만으로 끝내지 말고 운영 API를 한 번 실제 호출한다.

### 연설은 모델과 제한 시간이 따로다

연설은 `TALK_MODEL`(기본 `gpt-5.6-sol`)을 쓴다. 뼈대의 추론 강도는 `high`로 고정이고, 원고는 `TALK_DRAFT_EFFORT`(기본 `high`)를 따른다. 연구 답변용 `OPENAI_MODEL`과 `OPENAI_REASONING_EFFORT`는 연설에 적용되지 않는다.

연설의 OpenAI 요청 제한은 240초다(`OPENAI_TIMEOUT_MS`로 바꾼다). 함수가 먼저 죽으면 폴백조차 돌려주지 못하므로 함수 상한 300초보다 짧게 잡았다. 원고는 모델이 규칙을 어겼을 때 한 번 더 부른다. 두 호출이 모두 길면 합이 300초를 넘어 응답 없이 끊길 수 있다.

### 로그인 설정이 틀리면 조용히 뚫리거나 크게 실패한다

- `SESSION_SECRET`이 비어 있던 때는 빈 비밀로도 서명이 만들어져 누구나 세션을 위조할 수 있었다. 지금은 없거나 32자보다 짧으면 인증이 예외로 실패한다. 인증 API는 언제나, 다른 API는 세션 쿠키가 있을 때 실패한다. 값을 바꾸면 모두 로그아웃된다.
- 카카오가 돌아오는 주소는 `${APP_BASE_URL}/api/auth-callback`이고 카카오에 등록한 주소와 글자 하나까지 같아야 한다. 그래서 로그인은 `APP_BASE_URL`과 같은 호스트에서만 된다. 프리뷰 배포에서는 로그인이 되지 않는다.
- 화면은 `/api/options`가 어떤 이유로든 실패하면 로그인 화면으로 보낸다. 서버 오류도 로그아웃처럼 보이므로, 로그인이 풀린 것 같으면 그 API의 응답과 함수 로그를 먼저 본다.

### 로컬 실행도 실제 Blob 저장소를 쓴다

파일로 대신 저장하는 길은 없다. `npm run web`이 `.env`의 `BLOB_READ_WRITE_TOKEN`으로 실제 Blob 저장소에 읽고 쓴다. 운영 저장소의 토큰이면 로컬에서 만든 자료가 운영 자료를 덮어쓴다. 토큰이 없으면 읽기는 "없음"이 되고 주간 답변과 연설 저장은 조용히 건너뛰며, 설정 저장과 연설 지우기는 500으로 실패한다. 디스크에는 WOL HTML 캐시만 둔다(로컬 `.cache/wol`, Vercel `tmpdir()/jw-assistant-wol`).

### Windows에서 한글 경로의 재귀 삭제가 프로세스를 죽인다

Node 24.12의 `fs.rmSync({recursive:true})`는 Windows에서 절대경로에 한글이 있으면 `STATUS_STACK_BUFFER_OVERRUN`으로 프로세스를 죽인다. 이 저장소는 `바탕 화면` 아래에 있다. 그래서 `build:web`과 `smoke:web`은 OS 삭제 명령으로 먼저 지운 뒤 빌드한다. 이 방식을 Node 삭제로 되돌리지 않는다.

### 진행률은 실제 서버 단계가 아니라 예상치다

API는 완료 JSON을 한 번에 반환하므로 브라우저가 실제 세부 단계 진행률을 알 수 없다. 원형 게이지는 경과 시간을 기준으로 3%에서 시작해 180초에 94%, 최대 96%까지 올라가는 예상 진행률이며 응답이 성공한 뒤에만 100%가 된다. 연구 화면만 게이지를 쓰고 연설 화면에는 없다. 실제 진행률로 표시하거나 100%에서 서버를 기다리게 만들지 않는다.

실제 진행률이 필요해지면 요청을 작업 ID 기반 비동기 작업으로 바꾸고 스트리밍 또는 폴링 상태 API를 추가해야 한다.

## 5. 답변과 화면에서 유지해야 할 동작

- `(ㄱ)`과 `(ㄴ)`은 별도 답변 카드와 별도 `답변 복사` 버튼을 가진다.
- `토의해 보십시오`, `더 깊이 알아보기`, `교훈점 적용하기`, `시야를 넓혀 생각해 보기` 같은 소제목을 보존한다.
- 답변 영역은 연한 초록색이며 참고 성구와 시각적으로 구분한다.
- 별도 참고 자료가 있는 질문은 정확한 기사 항 범위 링크를 표시한다.
- 별도 참고 자료가 없는 질문도 해당 질문이 실린 공식 WOL 원문 링크를 표시한다.
- `답변 복사`는 `answer.답변`만 복사한다.
- 보관본을 열면 저장 안내와 `다시 만들기` 버튼을 보인다. 다시 만들기는 POST로 회중 공용본을 덮어쓰고 호출 비용이 든다. 연구 답변에는 지우기를 두지 않는다. 한 사람이 지우면 모두에게서 사라지기 때문이다.
- AI 답변은 보통 3문장부터 6문장으로 작성하고 원인과 결과, 시간 순서, 대조점, 실생활 의미를 필요한 만큼 연결한다.
- `문단의 흐름을 근거로 보면`, `성구 근거로는` 같은 반복 문구를 다시 넣지 않는다.
- 한국어 이외의 문자 체계가 섞이지 않도록 모델 지침과 출력 정규화를 유지한다.

## 6. 운영 명령과 배포 절차

### 로컬 실행과 검증

```bash
npm test
npm run typecheck
npm run smoke:web
npm run web
```

- `npm run web`은 화면을 빌드한 뒤 `src/web-server.mjs`로 정적 화면과 JSON API를 함께 띄운다. `.env`를 읽어 서버 환경 변수로 쓰는 명령은 이것뿐이다. 기본 주소는 `http://localhost:3000`이다. 다른 프로세스가 사용 중이면 PowerShell에서 `$env:PORT='3017'`처럼 포트를 바꾼 뒤 실행한다. 로그인은 `APP_BASE_URL`과 같은 주소에서만 되므로 포트를 바꾸면 그 값도 맞춘다.
- `npm run dev:web`은 Vite 개발 서버다. `/api`를 `localhost:3000`으로 넘기므로 `npm run web`도 함께 띄워 둔다.
- `npm run smoke:web`은 모든 화면을 SSR로 마운트해 예외가 없는지 본다. 컴포넌트 시험은 없다. 이 환경의 브라우저 확장은 localhost에 붙지 못하므로, 화면은 이 스모크와 사람의 육안으로 확인한다.

AI를 로컬에서 검증할 때는 `.env.example`을 참고하되 키 파일을 커밋하지 않는다.

### 환경 변수

값은 이 문서와 Git에 적지 않는다. 운영 값은 Vercel 프로젝트 설정에서, 로컬 값은 `.env`에서 관리한다.

| 이름 | 쓰는 곳 | 기본값과 주의 |
| --- | --- | --- |
| `OPENAI_API_KEY` | 모든 AI 호출 | 없으면 AI 대신 규칙과 공식 자료로 만든 폴백을 낸다 |
| `OPENAI_MODEL` | 연구 답변 | 기본 `gpt-5.6-terra` |
| `OPENAI_REASONING_EFFORT` | 연구 답변 | 기본 `high` |
| `OPENAI_BATCH_SIZE` | 연구 답변 | 기본 5 |
| `TALK_MODEL` | 연설 | 기본 `gpt-5.6-sol` |
| `TALK_DRAFT_EFFORT` | 연설 원고 | 기본 `high` |
| `OPENAI_TIMEOUT_MS` | 연설 | 기본 240000. 연구 답변은 120초 고정 |
| `KAKAO_REST_API_KEY` | 로그인 | 카카오 디벨로퍼스의 REST API 키 |
| `KAKAO_CLIENT_SECRET` | 로그인 | 카카오 로그인 Client Secret |
| `SESSION_SECRET` | 세션 서명 | 32자 이상. 바꾸면 모두 로그아웃된다 |
| `APP_BASE_URL` | 로그인 | 기본 `http://localhost:3000`. 카카오에 등록한 주소와 같아야 한다 |
| `BLOB_READ_WRITE_TOKEN` | 자료 보관 | `@vercel/blob`이 읽는다. Blob 저장소를 프로젝트에 연결하면 Vercel이 넣는다 |

### 참조 링크 갱신

평소에는 GitHub Actions가 매주 자동으로 돌린다(4절). 손으로 돌릴 때는 아래 명령을 쓴다. 풀지 못한 링크가 있으면 끝에 그 수를 알리고 종료 코드 1로 끝난다.

```bash
npm run refresh:references
npm test
```

갱신 뒤 `src/wol-reference-map.json`의 변경 수와 실패 경고를 확인한다. WOL 구조 오류를 단순 네트워크 오류로 간주하고 넘어가지 않는다.

### 운영 배포

`main`에 푸시하면 프로덕션 배포가 자동으로 만들어진다. 손으로 배포할 때는 아래 명령을 쓴다.

```bash
npx vercel --prod --yes
```

배포 뒤 아래 항목을 확인한다.

- `/`가 HTTP 200인지 확인한다.
- 로그인하지 않은 요청에 `/api/options`가 401을 돌려주는지, 로그인한 브라우저에서는 21주와 닉네임을 돌려주는지 확인한다.
- 화면 주소를 더했다면 그 주소를 직접 열어 404가 아닌지 확인한다.
- 생활과 봉사 또는 파수대 API를 확인할 때 GET은 보관본이 있으면 그것을 돌려준다는 점을 기억한다. 생성 경로까지 확인해야 할 때만 POST로 다시 만든다. POST는 비용이 들고 회중 공용본을 덮어쓴다. 새로 만들었으면 `generation.mode`, 답변 수, 참고 링크 수를 확인한다.
- Vercel 환경 변수 `OPENAI_API_KEY`가 Production에 설정되어 있는지 확인한다.
- 비밀 키나 출판물 본문이 브라우저 API 응답에 포함되지 않았는지 확인한다.

2026-08-09에 Vercel GitHub 앱을 `iam-kimleader/jw-assistant` 저장소에만 허용하고, Vercel 프로젝트를 GitHub 저장소와 연결했다. 검증 커밋 `c5a2740` 푸시 후 Vercel 프로젝트 API에서 `link.productionBranch`가 `main`이고 프로덕션 배포 `dpl_HBaXgMrm7xJaEJfezPJ3N7Y2dWTd`가 `READY`와 `PROMOTED` 상태임을 확인했다. 이후 운영 배포는 `main` 푸시로 자동 생성되며, 최신 배포 ID는 Vercel 대시보드나 API에서 확인한다.

## 7. 남은 위험과 다음 개발 순서

### 가장 높은 위험

- WOL HTML 클래스나 문서 구조가 바뀌면 질문과 참고 항 파서가 조용히 누락할 수 있다. 실제 주간 데이터 테스트를 유지한다.
- 회중 성서 연구 서책이 바뀌면 `서책심벌` 등록이 없어서 자동 조회가 실패한다.
- 참조 매니페스트의 주간 자동 갱신이 실패하면 새 주간의 참고 출판물 본문을 AI가 받지 못한다. 실패 메일이 오면 Actions 탭의 실행 기록을 먼저 본다.
- AI 답변은 공식 자료를 근거로 해도 생성 결과이므로 사실과 추론이 섞이지 않았는지 표본 검토가 필요하다. 연설 원고는 2026-10-29 개선 뒤 모델을 가짜로 둔 시험으로만 확인했고, 실제 OpenAI 호출로 품질을 본 적은 아직 없다.

### 운영상 제한

- 연구 답변 준비 시간은 약 2분이며 네트워크와 OpenAI 상태에 따라 달라진다.
- 진행률은 예상치다.
- 화면 선택지는 21주지만 준비 API 자체는 21주 범위로 제한하지 않는다.
- `package.json`의 Node 버전은 `>=24`여서 미래의 새 메이저 버전으로 자동 상승할 수 있다. 런타임 장애가 생기면 Node 24 고정 여부를 먼저 검토한다.
- 카카오 계정만 있으면 누구나 로그인해 AI 호출 비용을 쓸 수 있다.
- 연구 답변은 회중 공용 한 벌이라 누가 다시 만들면 모두의 답이 바뀐다.
- 알면서 미룬 결함이 있다. 자료를 잃거나 돈이 나가지는 않는다. 나머지는 `context-notes.md`의 2026-08-27, 2026-08-28 항목에 있다.
  - `src/store.mjs`의 읽기는 "없음"과 "실패"를 구분하지 못한다. 설정 저장 중에 읽기가 실패하면 닉네임과 첫 로그인 때가 지워질 수 있다.
  - Blob 목록은 쪽 나누기 없이 한 번에 1000개까지만 읽는다. 넘으면 뒤가 잘린 채 조용히 보인다.
  - 공개강연 카드는 제목이 늘 `일요일 공개강연`이라, 같은 주에 준비한 두 공개강연을 구분하지 못한다.

### 아직 구현하지 않은 기능

- 개인 연구.
- 봉사인도.
- 주제 연구와 성구 및 주제 노트 승격 체계.
- 통독과 개인별 진도 관리.
- 실제 서버 단계 기반 진행률.

추가 기능은 기존 브라우저가 JSON API만 호출하는 경계를 유지한다. WOL 접근, 성경 코어 접근, AI 키와 답변 생성, Blob 경로 만들기는 계속 서버에 둔다.
