# 봉사인도 설계 — 노션 봉사모임 원고 이어 쓰기

- 작성일은 2026-08-21이다.
- 현행 운영 정본은 `docs/핵심-운영-인수인계.md`이며 이 문서는 그 위에 새 기능 하나를 더한다.
- 이 기능은 당분간 로컬 전용이다. 이유는 5절에 있다.

## 1. 무엇을 만드는가

화면의 비활성 카드로만 있던 `봉사인도`를 구현한다. 김동언 형제의 노션 `봉사모임`
데이터베이스를 읽어 지금까지 다룬 주제의 흐름을 파악하고, WOL 「야외 봉사」 출판물
색인의 공식 소제목 가운데 다음에 다룰 것을 후보로 제시한 뒤, 고른 주제로 봉사모임
원고를 만들어 형제가 확인한 뒤에만 노션에 새 행으로 저장한다.

핵심 요구는 "현재 게시물과 다음 만들 게시물을 전략적으로 잇는 것"이다. 이미 노션
순번 10 「재방문을 실제로 하십시오」가 그 규격을 보여 준다.

> 지난 5월 22일에 우리는 "재방문을 위한 토대를 놓으십시오"를 함께 살펴보았습니다.
> 오늘은 그다음 단계 — 놓은 토대 위에 실제로 다시 찾아가는 것을 생각해 봅니다.

생성되는 모든 원고의 들어가는 말은 이 형태로 직전 글을 명시적으로 이어받는다.

## 2. 확인된 사실

### 노션

- 데이터베이스 이름은 `봉사모임`이고 경로는 `[S1]——김리더——— › 봉사모임`이다.
- 데이터베이스 ID는 `38276147-3735-80e4-99ca-cb4e81cb6c53`이다.
- 데이터 소스 ID는 `38276147-3735-8052-9617-000bfb210bd9`이다.
- 속성은 `순번`(number), `날짜`(date), `제목`(title) 세 개뿐이다.
- 2026-08-21 기준 순번 1부터 11까지 있고 날짜는 2026-05-15부터 2026-08-01까지다.
- 순번 11은 제목이 비어 있는 초안이다.
- 과거 11개 중 9개가 금요일이다.
- 완성된 원고는 6단이다. 오늘의 주제, 들어가는 말, 성구 근거, 핵심 생각,
  오늘 실천할 제안, 마무리 격려다. 실천 제안은 체크박스다.

### WOL 「야외 봉사」 색인

- 문서 ID는 `1200272149`이고 「워치 타워 출판물 색인 1986-2026」의 항목이다.
- 조회 URL은 `https://wol.jw.org/ko/wol/d/r8/lp-ko/1200272149`이고 조회일은 2026-08-21이다.
- `p.su` 소제목이 295개, `p.sv` 하위 항목이 482개다.
- 출판물 약칭은 전부 `/ko/wol/pc/...` 링크다. 링크는 2,591개다.
- 이 `/pc/` 형식은 `src/publication-reference.mjs`가 이미 해석하는 형식과 같다.

## 3. 구성 요소

### 새로 만드는 파일

| 파일 | 역할 |
|---|---|
| `src/notion-client.mjs` | 노션 REST v1 최소 클라이언트 |
| `src/service-topics.mjs` | 색인 파서와 주제 매니페스트 로더 |
| `src/service-meeting.mjs` | 후보 선정과 원고 조립 |
| `src/openai-text.mjs` | 자유 형식 텍스트용 최소 OpenAI 호출 |
| `scripts/refresh-service-topics.mjs` | 주제 매니페스트 생성기 |
| `src/service-topics.json` | 생성된 주제 매니페스트 |

### 그대로 재사용하는 것

- `src/wol-fetch.mjs`의 `fetchCached`와 `resolveRedirect`.
- `src/html-text.mjs`의 `htmlToText`.
- `src/publication-reference.mjs`의 `parsePublicationDocument`와 `selectPublicationContent`.
- `src/verse-address.mjs`의 `loadIndex`와 `parseReference`.
- `src/bible-text.mjs`의 `createTextReader`.

### 의도적인 중복 하나

`src/ai-answer.mjs`는 `enhanceAnswersWithAI` 하나만 내보내고 내부의 OpenAI 호출은
답변 배열 전용이다. 봉사모임 원고는 자유 형식이라 그 함수를 쓸 수 없다. 공용
헬퍼를 추출하려면 15개 답변 생성이라는 검증된 운영 경로를 수정해야 한다.

그래서 새 기능만 사용하는 `src/openai-text.mjs`를 따로 둔다. OpenAI Responses API
호출과 오류 요약이 두 파일에 각각 존재하게 된다. 이 저장소는 `extract-refs.mjs`와
`verify-refs.mjs`에서 같은 이유로 중복을 택한 선례가 있다. 나중에 세 번째 호출부가
생기면 그때 추출한다.

## 4. 데이터 흐름

준비를 한 번에 끝내지 않고 세 단계로 나눈다. 형제가 후보를 직접 고르기 때문이다.

### 1단계 — 후보 제시

```
GET /api/service-meeting/candidates
```

1. 노션에서 `봉사모임` 행 전체를 읽는다. 순번, 날짜, 제목이다.
2. 순번이 가장 큰 완성 글의 본문을 읽는다. 제목이 빈 행은 건너뛴다.
3. `src/service-topics.json`을 읽는다. 네트워크를 쓰지 않는다.
4. AI에게 과거 제목 목록과 주제 라벨 777개를 주고 후보 3개와 선정 이유를 받는다.
5. 서버가 매니페스트에 실제로 있는 라벨만 통과시킨다. 없는 라벨은 버린다.

응답은 후보 3개다. 각 후보는 라벨, 상위 주제, 선정 이유, 참고 표시 문구를 갖는다.
출판물 본문은 이 단계에서 조회하지 않는다.

OpenAI 키가 없거나 호출이 실패하면 규칙으로 후보를 고른다. 과거 제목에 쓰인 낱말과
겹치지 않는 라벨 가운데, 참고 링크가 많고 최근 출판물 약칭을 포함한 것을 앞에 둔
3개다. 이때 선정 이유는 `자동 선정 — 아직 다루지 않은 주제임.`으로 표시해 AI가 고른
것과 구분한다. 후보가 비어 있는 채로 돌려주지 않는다.

### 2단계 — 원고 생성

```
POST /api/service-meeting/draft   { "주제라벨": "...", "날짜": "YYYY-MM-DD" }
```

1. 그 주제의 `/pc/` 링크를 최대 4개까지 `resolveRedirect`로 `/d/...#h=` 범위로 바꾼다.
2. 각 `/d/` 문서를 `fetchCached`로 받고 `selectPublicationContent`로 해당 항만 고른다.
3. AI에게 출판물 본문, 직전 글의 날짜와 제목과 요약, 7단 형식을 주고 원고를 받는다.
4. AI가 돌려준 성구 주소를 서버가 검증하고 로컬 본문을 채운다. 6절에서 자세히 다룬다.

### 3단계 — 노션 저장

```
POST /api/service-meeting/save    { "원고": {...}, "순번": 12, "날짜": "...", "제목": "..." }
```

1. 저장 직전에 노션을 다시 읽어 같은 순번 또는 같은 날짜의 행이 있는지 확인한다.
2. 있으면 만들지 않고 이유를 돌려준다.
3. 없으면 `POST /v1/pages`로 새 행 하나를 만든다.

브라우저는 JSON API만 호출한다. WOL 접근, 성경 코어 접근, OpenAI 키, 노션 토큰은
모두 서버에 남는다. 기존 두 기능의 경계와 같다.

## 5. 왜 로컬 전용인가

`docs/핵심-운영-인수인계.md`에 기록된 대로 WOL `/pc/` 경로는 Vercel 서울 리전에서도
반복해서 `ETIMEDOUT`이 난다. 실제 기사 `/d/` 경로만 안정적이다.

이 기능은 2단계에서 후보 주제의 `/pc/` 링크를 실시간으로 해석해야 근거를 얻는다.
따라서 지금 배포하면 원고의 출판물 근거가 비게 된다. 로컬 전용은 취향이 아니라
현재의 기술적 제약이다.

나중에 배포하려면 자주 쓰는 주제의 `/pc/` 해석 결과를 매니페스트에 함께 저장하면
된다. `src/wol-reference-map.json`이 이미 그 방법으로 같은 문제를 풀었다. 3절의
매니페스트 구조는 그 확장을 미리 염두에 둔 것이다.

이번 범위에서는 `api/*.js` 어댑터를 만들지 않고 `vercel.json`도 수정하지 않는다.

## 6. 원고 형식과 정확성 규칙

원고는 7단이다.

1. 오늘의 주제
2. 들어가는 말
3. 성구 근거
4. 핵심 생각
5. 오늘의 대화 시연
6. 오늘 실천할 제안
7. 마무리 격려

### 들어가는 말

직전 글의 날짜와 제목을 반드시 포함하고, 오늘 주제가 왜 그다음인지 한 문장으로
잇는다. 직전 글이 없으면 그 사실을 밝히고 첫 회차로 연다.

### 성구 근거

**AI는 성구 문장을 쓰지 않는다. 주소만 돌려준다.** 서버가 `parseReference`로 주소를
해석하고 `core/bible/text/`에서 실제 문자열을 읽어 채운다.

주소가 해석되지 않으면 그 칸을 비우고 `성구 자동 확인 실패`를 표시한다. AI가 쓴
성구 문장을 그대로 쓰는 경로는 만들지 않는다. 영적 보물 2의 `selectedVerse` 검증과
같은 방식이다.

### 오늘의 대화 시연

집주인과 형제의 대화를 짧게 시연한다. 노션 순번 11 초안의 형식을 따른다. 대화 안에
성구를 인용할 때도 본문은 로컬 파일에서만 온다.

### 핵심 생각

2단계에서 뽑은 실제 출판물 본문 안에서만 만든다. 원고 하단에 그 출판물의 제목,
`/d/...#h=` 링크, 조회일을 남긴다. 출판물 근거를 찾지 못한 문장에는
`출판물 근거 미확인 — 내 정리임.`을 붙인다.

### 언어

한국어 문장은 마침표로 끝낸다. 문장 끝에 콜론을 쓰지 않는다. 한국어 이외의 문자
체계가 섞이지 않도록 기존 답변 생성과 같은 정규화를 적용한다.

## 7. 주제 매니페스트

`npm run refresh:service-topics`가 색인 문서 `1200272149` 하나를 읽어
`src/service-topics.json`을 만든다. 저장하는 것은 라벨과 링크 쌍뿐이며 출판물 본문은
담지 않는다. `src/wol-reference-map.json`과 같은 규칙이다.

```json
{
  "관심이 자라게 함": {
    "상위": null,
    "참고": [
      { "표시": "파19.07 15-16", "pc": "/ko/wol/pc/r8/lp-ko/1200272149/23/0" },
      { "표시": "파16.08 27-28", "pc": "/ko/wol/pc/r8/lp-ko/1200272149/23/2" }
    ]
  },
  "도달하기 위해 받을 수 있는 도움": {
    "상위": "개인적 목표",
    "참고": [
      { "표시": "파94 9/15 14-15", "pc": "/ko/wol/pc/r8/lp-ko/1200272149/12/0" }
    ]
  }
}
```

`p.su`는 `상위`가 `null`이고 `p.sv`는 직전 `p.su`를 가리킨다.

기준선은 소제목 295개, 하위 항목 482개, 링크 2,591개다. 추출 수가 기준선보다 줄면
스크립트가 경고하고 종료 코드 1로 끝난다. 파서가 조용히 얇아지는 것을 막는 기존
인용 결산과 같은 원칙이다.

## 8. 노션 클라이언트

API 버전은 `2022-06-28`을 쓴다.

| 기능 | 요청 |
|---|---|
| 행 조회 | `POST /v1/databases/{database_id}/query` |
| 본문 읽기 | `GET /v1/blocks/{page_id}/children` |
| 행 생성 | `POST /v1/pages` |

### 안전장치

- `PATCH`와 `DELETE`를 클라이언트에 넣지 않는다. 기존 행을 고치거나 지우는 경로가
  코드에 존재하지 않는다.
- 저장 직전에 중복을 다시 확인한다. 같은 순번 또는 같은 날짜가 있으면 만들지 않는다.
  `집회준비`가 예습지를 덮어쓰지 않고 멈추는 것과 같은 규율이다.
- 순번 기본값은 기존 최댓값 더하기 1이다. 날짜 기본값은 다음 금요일이다. 둘 다
  화면에서 고칠 수 있다.
- 제목이 비어 있는 행이 있어도 그 행을 채우지 않는다. 항상 새 행을 만든다. 순번 11
  같은 미완성 초안은 형제가 직접 쓰고 있는 것일 수 있으므로 건드리지 않는다.

### 블록 구성

실천 제안은 `to_do` 블록으로 만들어 기존 글의 체크박스와 같은 모양이 되게 한다.
나머지 단은 `heading_2`와 `bulleted_list_item`으로 만든다.

## 9. 설정

`.env.example`에 두 줄을 더한다. `.env`는 이미 `.gitignore`에 있다.

```
NOTION_TOKEN=
NOTION_SERVICE_DB_ID=38276147-3735-80e4-99ca-cb4e81cb6c53
```

형제가 직접 해야 하는 준비가 하나 있다. `notion.so/my-integrations`에서 내부 통합을
만들고, 노션에서 `봉사모임` 페이지를 그 통합에 공유한 뒤, 발급된 토큰을 `.env`에
넣어야 한다. 이 단계는 사람만 할 수 있다.

토큰이 없으면 후보 화면이 `노션 토큰 미설정`을 표시하고 멈춘다. 조용히 빈 목록을
돌려주지 않는다.

## 10. 오류 처리

| 상황 | 동작 |
|---|---|
| 노션 토큰 없음 | 명시적으로 표시하고 멈춘다 |
| 노션 호출 실패 | 상태 코드와 요약을 표시하고 멈춘다 |
| WOL `/pc/` 해석 실패 | 그 링크만 근거 없이 남기고 나머지로 원고를 만든다 |
| 출판물 본문 조회 실패 | 같다. 전체 실패로 번지지 않는다 |
| OpenAI 키 없음 또는 호출 실패 (후보 단계) | 규칙으로 고른 후보 3개를 돌려준다 |
| OpenAI 키 없음 또는 호출 실패 (원고 단계) | 출판물 본문과 성구로 만든 결정론적 초안을 돌려준다 |
| 성구 주소 검증 실패 | 성구 칸을 비우고 경고를 표시한다 |
| 노션 저장 중복 | 만들지 않고 이유를 돌려준다. 원고는 화면에 남는다 |
| 노션 저장 실패 | 원고를 화면에 그대로 둔 채 알린다 |

어느 경우에도 성구 문장은 `core/bible/text/`에서만 온다.

## 11. 화면

상단 내비게이션과 홈 카드에 `봉사인도`를 활성으로 바꾼다. 화면은 세 부분이다.

1. 후보 영역. 후보 3개를 라디오로 보여 주고 각각 선정 이유를 함께 표시한다.
2. 원고 영역. 7단을 순서대로 보여 준다. 출판물 링크와 조회일을 하단에 둔다.
3. 동작 영역. `원고 복사`와 `노션에 저장`이다. 순번과 날짜와 제목을 고칠 수 있다.

`원고 복사`는 원고 본문만 복사한다. 출판물 링크와 선정 이유는 넣지 않는다. 기존
`답변 복사`의 규칙과 같다.

진행률 게이지는 만들지 않는다. 각 단계가 짧아 필요하지 않다.

## 12. 테스트

전부 픽스처 기반이며 네트워크를 타지 않는다.

- 색인 파서. `p.su`와 `p.sv` 중첩, `/pc/` 링크 추출, 상위 연결.
- 매니페스트 기준선 감시. 추출 수가 줄면 실패한다.
- 노션 응답 파서. 행 목록과 블록 본문을 객체로 바꾼다.
- 노션 쓰기 본문 생성. `to_do` 블록과 속성 형식을 검사한다.
- 중복 저장 거부. 같은 순번과 같은 날짜 각각을 검사한다.
- 성구 주소 검증. 유효한 주소는 로컬 본문으로 채워지고, 잘못된 주소는 거절되며
  AI가 쓴 문장이 절대 통과하지 않는 것을 검사한다.
- 다음 순번과 다음 금요일 계산. 제목이 빈 행이 있어도 새 순번을 쓰는 것을 검사한다.
- 키가 없을 때 후보가 비어 있지 않고 규칙 선정 표시가 붙는 것을 검사한다.
- 들어가는 말이 직전 글의 제목을 포함하는지 검사한다.

기존 172개 위에 더한다.
